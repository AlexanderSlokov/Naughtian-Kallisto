# ADR-0017: Distribute Kallisto through Homebrew

> Draft, written as it went over four rounds of interview on 2026-10-18. Twelve questions are settled.
> What is still open is under *Open questions*; the ADR becomes `accepted` once those have answers.

## Context and Problem Statement

Up to 2.0.2, Kallisto ships one thing: a Docker image (`main-publish.yml`, `nightly.yml`). GitHub Releases
carry no binaries. Anyone who wants to run Kallisto outside a container has to `cargo build` it.

Goal: package Kallisto for Homebrew, so installing it is cleaner for both kinds of user, Dev and Ops.
Why Homebrew: it lets someone try the CLI without depending on a Docker daemon, which is how Vault,
Consul and Boundary are distributed.

The repository builds two binaries, `kallisto-server` and `kallisto-ctl`. On macOS the main job is sealing
files with `kallisto-ctl`; the server is there so Mac users can try Kallisto, not to serve production.

What is known about platforms, from the code at 2.0.2:

- `kallisto-server` is designed for Linux. Three places depend on it directly:
  - `src/event/cpu_plan.rs` reads the topology from `/sys/devices/system/cpu` to pin workers (ADR-0016).
  - `src/server/listener.rs` relies on `SO_REUSEPORT` for the kernel to spread connections across
    workers. On macOS the option exists but does not balance load, so thread-per-core buys nothing there.
  - `components/kallisto_crypto/src/hardening.rs` calls `prctl(PR_SET_DUMPABLE)`, already behind
    `cfg(target_os = "linux")`.
- No CI job builds or tests on macOS.
- `aws-lc-rs` (the barrier, ADR-0015 D13) is a C library. Building it for a target needs a C compiler for
  that target, so cross-compiling from an x86_64 runner is not cheap.

## Decision Drivers

1. Installing and uninstalling leaves nothing outside Homebrew's prefix. No Docker daemon, no Rust on the
   user's machine.
2. Two kinds of user, one package: Dev on a Mac seals files and tries the server; Ops on Linux has
   `kallisto-ctl` on every machine.
3. Nothing that ADR-0015 and ADR-0016 set is weakened: static binaries on Linux, and the hot read path is
   promised on Linux only.
4. A user can check which commit the binary they installed was built from, not only that it matches a sha256.
5. One maintainer: a release must not gain any manual step.

## Considered Options

1. Keep things as they are: Docker image only.
2. A formula that builds from source (`depends_on "rust" => :build`).
3. A formula that downloads prebuilt binaries from the GitHub Release, with a hand-written workflow (chosen).
4. As option 3, but with cargo-dist generating the workflow and the formula.

## Decision Outcome

Option 3. The detailed decisions:

- **Q1.** One formula installs both `kallisto-server` and `kallisto-ctl`.
- **Q2.** Homebrew on both macOS and Linux.
- **Q3.** The formula lives in a tap of our own, `AlexanderSlokov/homebrew-tap`, not in homebrew-core.
- **Q4.** The formula downloads prebuilt binaries. CI builds a tarball per platform and attaches it to the
  GitHub Release; the formula downloads it and checks its sha256 (as `hashicorp/tap` does). The user's
  machine needs no Rust.
- **Q5.** On macOS the server starts normally and prints one warning line at startup: no CPU pinning, no
  load spreading, for trying out only.
- **Q6.** Three targets: `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`.
  No build for Intel Macs.
- **Q7.** A workflow written in this repository: build the three targets, attach the tarballs to the
  Release, then push the new formula (version, sha256) to the tap. Actions pinned by SHA like the existing
  workflows. No cargo-dist.
- **Q8.** The formula has no `service` block. The server under Homebrew is started and stopped by hand.
  Production on Linux still goes through Docker/K8s, or systemd managed by Ops.
- **Q9.** Beyond the sha256 Homebrew checks, every tarball has a GitHub artifact attestation (Sigstore build
  provenance), checked with `gh attestation verify`. No Apple notarization.
- **Q10.** The formula is named `naughtian-kallisto`: `brew install alexanderslokov/tap/naughtian-kallisto`.
  It matches the repository and crate names, and is less likely to collide if it is ever submitted to
  homebrew-core.
- **Q11.** The workflow pushes to the tap with a deploy key that can write to the tap repository only,
  stored as a secret of this repository.
- **Q12.** It ships in 2.1.0. A new distribution channel and a new behaviour on macOS are a feature, not
  a patch.

### Consequences

- Good: `brew install` on a Mac or on Linux gives both binaries in seconds; `brew uninstall` removes them cleanly.
- Good: the Linux tarball holds the same kind of static musl binary as the Docker image, so Ops has a binary
  for systemd without an image.
- Good: every tarball traces back to the commit and the workflow that built it.
- Bad: macOS becomes a first-class target, and the hot read path was not designed for it. CI on macOS is
  required so that we never ship a binary whose tests never ran.
- Bad: each target is built on its own native runner (`macos-14`, `ubuntu-24.04`, `ubuntu-24.04-arm`) to
  avoid cross-compiling `aws-lc-rs`. A release takes as long as its slowest job, and macOS runners cost
  several times more CI minutes than Linux ones.
- Bad: one more repository (the tap) and one more secret (the deploy key) to keep.
- Neutral: Intel Macs get no binary. Whoever needs one can `cargo build`.

### Confirmation

- On a clean Apple Silicon Mac and a clean x86_64 Linux machine, `brew install alexanderslokov/tap/naughtian-kallisto`
  installs, `brew test naughtian-kallisto` passes, and `brew uninstall` leaves no file outside the prefix.
- `kallisto-server` on macOS prints exactly one warning line at startup and serves `/v1/sys/health`.
- `gh attestation verify <tarball> --repo AlexanderSlokov/Naughtian-Kallisto` passes for all three tarballs.
- Pushing the 2.1.0 tag updates the formula in the tap with no manual step.
- Rust CI has a macOS job running `cargo test --workspace`.

## Pros and Cons of the Options

### Option 1 — Keep things as they are, Docker image only

- Good: no new work.
- Bad: every use of `kallisto-ctl` needs a Docker daemon, against driver 1. Ops has no binary for systemd.

### Option 2 — Formula builds from source

- Good: no build matrix in CI; Homebrew builds on the user's machine.
- Bad: every install takes minutes and needs a C compiler for `aws-lc-rs`.
- Bad: Homebrew uses stable Rust, the repository pins `nightly-2026-05-24`. What gets built on the user's
  machine is not what CI tested.
- Bad: no build provenance for what the user runs, against driver 4.

### Option 3 — Prebuilt binaries, hand-written workflow (chosen)

- Good: meets all five drivers.
- Good: same pinned toolchain and same pinning of actions by SHA as the existing workflows.
- Bad: we write and keep the release workflow ourselves, build matrix, attestation and the push to the tap included.

### Option 4 — cargo-dist

- Good: `dist init` generates the workflow, the tarballs and the formula. Least work at the start.
- Bad: the release workflow is generated by the tool and will be generated again. Actions pinned by SHA,
  the pinned nightly toolchain and a native runner per target become things to argue with the tool about
  instead of things we wrote.

## More Information

### Open questions

1. `kallisto-ctl --version` cannot work as expected: `--version` is already an argument of `seal`, the
   version of the file (`cmd/kallisto-ctl/src/args.rs:32`). It is the first thing a Homebrew user will type.
   Add a `version` subcommand to both binaries? Rename the `seal` argument?
2. What does the formula's `test` block check? Proposal: seal and then check a small file with
   `kallisto-ctl`, which proves the binary works rather than only that it prints a version.
3. Does the macOS build compile at all? Nobody has tried. `cargo build` on `aarch64-apple-darwin` has to run
   before Q5 is final.
4. Does a stable toolchain build it? The repository uses no `#![feature]`, but this has not been checked.
5. Should a warning also be printed on Linux when load cannot be spread, for example when `spec.cpus` holds
   a single CPU? Or on macOS only?
6. Tarball name and layout: `naughtian-kallisto-2.1.0-aarch64-apple-darwin.tar.gz`, holding both binaries,
   `LICENSE` and `THIRD-PARTY-NOTICES.md`?
7. Will #58 (ring or aws-lc-rs for TLS) land before 2.1.0? Dropping `ring` makes the tarball smaller, so
   tarball size should be measured after #58.
