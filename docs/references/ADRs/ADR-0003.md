## Context and Problem Statement

Kallisto needs a configuration format for its deployment. The choice of configuration language (e.g., HCL, YAML) and its schema design significantly impacts operators' experience, especially when deploying on Kubernetes alongside related projects like Helvilette. We need to decide on the syntax, structure, and validation mechanism for Kallisto's configuration.

## Decision Drivers

* Kallisto is primarily deployed on Kubernetes using DaemonSet and ConfigMap.
* Need consistency with Helvilette, which uses a Kubernetes-style YAML format.
* The configuration must enforce correct combinations of settings at parse-time (e.g., preventing `proxy` settings when running in `sovereign` role).
* Configuration overrides must follow standard 12-factor app patterns, specifically allowing environment variables to override file configurations for node-specific settings.
* The format should support easy validation in CI environments.

## Considered Options

* HCL (HashiCorp Configuration Language)
* YAML (Kubernetes-shaped with `apiVersion`, `kind`, and specific role blocks)

## Decision Outcome

Chosen option: "YAML (Kubernetes-shaped)", because Kubernetes is the primary deployment environment and YAML integrates natively with its tooling (Kustomize, Helm, ConfigMaps). 

Additionally, HCL support in Rust (`hcl-rs`) is incomplete regarding HCL2 semantics, which would lead to a subpar experience for users expecting full Terraform-like expressions. 

The configuration schema will be strongly typed using Rust's `serde` with tagged enums to ensure invalid configurations fail at parse-time rather than silently during runtime.

### Consequences

* Good, because it integrates seamlessly with Kubernetes configuration management tools.
* Good, because it aligns with Helvilette's configuration style, reducing the learning curve for operators managing both.
* Good, because using tagged enums in `serde` allows the compiler to enforce strict boundaries (e.g., `role: proxy` alongside a `sovereign` block will fail to parse).
* Good, because it allows supporting both JSON and YAML almost for free with `serde_json` and `serde_yaml` forks.
* Bad, because YAML has known quirks (e.g., implicit typing issues like `no` becoming `false`, whitespace sensitivity).

### Confirmation

* The configuration struct will use `#[derive(Deserialize)]` with `#[serde(deny_unknown_fields)]` to catch typos.
* A `kallisto validate --config x.yaml` command will be implemented to allow checking configurations without starting the server, enabling CI validation.
* Configuration overriding must strictly follow the priority: `CLI > env > file > defaults`.

## Pros and Cons of the Options

### HCL

* Good, because it is familiar to Terraform users.
* Bad, because `hcl-rs` only parses syntax, lacking full HCL2 semantics (variables, functions, dynamic blocks).
* Bad, because Kallisto's provisioning of internal contents via API (which uses HCL/Terraform) is conceptually separate from its deployment configuration.

### YAML (Kubernetes-shaped)

* Good, because it natively fits into ConfigMaps, Kustomize patches, and Helm values.
* Good, because we can leverage `apiVersion: kallisto/v1` to version the API without breaking old configurations.
* Neutral, because while YAML has quirks, the validation is strictly guarded by Rust's `serde`.

## More Information

* **Secret Management:** Secrets must never be stored inline in the configuration file. Only references like `tokenFile:` or `${ENV_VAR}` should be used to ensure the configuration file itself doesn't become a secret and can be safely committed to Git.
* **Minimal Configuration:** The minimal working configuration should be kept under 10 lines, relying on sensible defaults for most options.
* **YAML Parser:** Since `serde_yaml` is archived, we will evaluate active forks like `serde_yaml_ng` or `serde_norway`.
* **Fixing Helvilette:** The configuration priority in Helvilette currently uses `CLI > YAML > env > defaults`, which breaks node-specific env injections. It must be fixed to match Kallisto's `CLI > env > file > defaults`.
