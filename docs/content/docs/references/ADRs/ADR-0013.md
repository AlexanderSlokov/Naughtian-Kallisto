# ADR-0013: Verification Strategy

> [!NOTE]
> **Sửa đổi bởi [ADR-0015](./ADR-0015.md) — The Duck Turn (2026-09-16).** Trạng thái giữ nguyên; chỉ phạm vi thay đổi.
>
> Trọng tâm xác minh chuyển sang **bộ test tương thích Vault SDK thật + các ca xấu** làm ưu tiên số một, thay vì phủ rộng đều (**ADR-0015, mục Confirmation**).

## Context and Problem Statement

Kallisto holds secrets. A domain logic bug here leaks credentials, drops versions, or serves revoked data.

Current testing: inline unit tests with handwritten mocks, `tests/e2e_vault_compat.rs` for Vault compatibility, `tests/integration/test_persistence.sh`, and an empty `fuzz/` directory. This suite catches regressions; it cannot prove correctness.

Another factor: AI agents write a notable chunk of the code. We need machine-gradable verification that does not depend on reviewer alertness.

The question: which tools, across what scope, and at what cost?

## Decision Drivers

* Verification must not block the critical path for Phase 3/4 or the CNCF Sandbox application.
* Must run in CI and in agent environments (Claude Code). If a tool cannot build inside a container, it does not exist.
* Prioritize catching real bugs in real code over tools that look prestigious on a proposal.
* Apache-2.0 compliance: tooling runs at build/test time only, without imposing license constraints on released artifacts.

## Considered Options

* Option 1: Status quo (unit tests + e2e compatibility tests).
* Option 2: All-in formal verification (Creusot/Rocq across the entire codebase).
* Option 3: Tiered approach (assign each code layer a tool matched to its cost-to-benefit ratio).

## Decision Outcome

Adopt Option 3.

Why reject Option 2: deductive verifiers (Creusot, Prusti, Aeneas) cannot handle `unsafe` and concurrency structurally. Those areas carry Kallisto's highest risks (`LockFreeQueue`, `ShardedCuckooTable`, `rkyv::archived_root`). An all-in formal approach spends the most effort where it yields the least.

### 1. Selected Toolchain

#### Tier 1: Adopt (runs on every PR)

| Tool | Target | Catches |
|---|---|---|
| `proptest` + model oracle | `kallisto_kv_model` | KV-v2 semantic drift, operation sequence edge cases |
| `miri` | `rkyv::archived_root`, `LockFreeQueue`, `unsafe impl Send/Sync` | Undefined behavior, data races, memory leaks |
| `loom` | `LockFreeQueue::{enqueue,dequeue}`, `ShardedCuckooTable` | Memory ordering flaws, lost updates |
| `cargo-fuzz` | HTTP parser, rkyv deserialization | Panics and crashes on untrusted input bytes |
| `cargo-mutants` | Entire workspace | Test suite quality (identifies tests that pass without asserting anything real) |

#### Tier 2: Pilot (non-blocking CI)

| Tool | Target | Notes |
|---|---|---|
| `Creusot` 0.11.x | `kallisto_kv_model` crate only | INRIA/CNRS. Pinned to a specific nightly toolchain; runs with `allowed_failure: true` |

#### Tier 3: Defer to 1.2.0

| Tool | Target |
|---|---|
| `TLA+` / TLC | Control plane / data plane protocols: lease invalidation, gossip, Raft interaction. Written before implementation |

#### Rejected Options (Rationale recorded to prevent relitigating)

* **B-Method / Atelier B (ClearSy)**: Refinement tool for safety-critical hardware (e.g., Paris Metro Line 14). Primary tool is proprietary; learning curve takes months. TLA+ yields comparable protocol-level value at a fraction of the cost, with public Raft specifications available for reference.
* **Frama-C (CEA), Astrée, SCADE/Lustre**: Built for C/C++ and synchronous control systems. Not applicable to Rust.
* **F\* / HACL\***: Kallisto does not implement custom cryptography. Selecting verified crypto dependencies falls under ADR-0012, not this ADR.
* **Verus**: Requires macro-extended Rust that invades the entire codebase.
* **Prusti**: Overlaps with Creusot, with slower development pace.
* **Kani**: Re-evaluate if Loom hits state-space explosion. Current limits: bounded verification, monomorphic code only.
* **shuttle**: Backup for Loom under excessive state space. Not adopted at this stage.

### 2. Prerequisite: `kallisto_kv_model` Crate

`KvEngine::put_version` cannot be verified in its current form because business logic is interleaved with I/O (`enqueue_or_execute`, `cache.insert`, and `path_index.insert_path_if_absent` sit directly in the function body).

This requires extracting a pure crate with no async, no I/O, and no `unsafe`:

```rust
pub enum KvOp {
    Put { payload_len: usize, cas: Option<u32> },
    SoftDelete { version: u32 },
    Undelete { version: u32 },
    Destroy { version: u32 },
    UpdateMeta { max_versions: u32, cas_required: bool, delete_version_after_ms: u64 },
}

pub enum Effect {
    WriteVersion { version: u32 },
    DeleteVersion { version: u32 },
    WriteMeta,
    IndexPath,
}

/// Single state transition function. Pure: identical inputs yield identical outputs.
pub fn apply(
    meta: &KeyMetadata,
    op: KvOp,
    now_ms: u64,
) -> Result<(KeyMetadata, Vec<Effect>), EngineError>;
```

`KvEngine` then reduces to: read metadata -> call `apply` -> execute the list of `Effect` values. No business decisions remain outside `apply`.

This is a hard prerequisite for V1 and beyond. It is worth doing even if this entire verification effort were cancelled, because it makes KV-v2 logic testable, directly comparable to Vault, and readable.

### 3. Invariants to Verify

#### Group A: KV-v2 Semantics (`proptest`, then `Creusot`)

| ID | Invariant |
|---|---|
| A1 | `current_version` is monotonically increasing; it never decreases |
| A2 | `versions` is ordered ascending by `version_id`, with no duplicates |
| A3 | `destroyed = true` is terminal; no operation can reverse it |
| A4 | CAS mismatch leaves state untouched byte-for-byte; no partial mutations |
| A5 | Round-trip: `put` followed by `read` of that version returns the exact payload written |
| A6 | `undelete ∘ soft_delete = identity` for non-destroyed versions |
| A7 | `versions.len() ≤ max_versions` after trimming |
| A8 | `destroy` deletes payload but retains `VersionState` in metadata |
| A9 | The mapping `(path, version) -> storage key` is injective |

A7 requires verification before testing. In current `put_version`, `meta.versions.push(vs.clone())` runs without trimming against `max_versions`. If confirmed, metadata grows unboundedly with write volume, diverging from Vault semantics (Vault purges the oldest version when exceeding `max_versions`). Verify this in code before writing tests.

A9 is a potential security vulnerability, not a theoretical exercise. `build_meta_key` produces `m:{path}`, and `build_version_key` produces `v:{path}:{version}`. If `path` allows `:`, two distinct `(path, version)` pairs can collide on the same storage key. An attacker crafting paths with colons could read or overwrite another path's versions. Either prove injectivity under current path validation or switch to length-prefixed or escaped encoding.

#### Group B: Concurrency (`loom`)

| ID | Invariant |
|---|---|
| B1 | `LockFreeQueue`: enqueued items are never lost; items are never dequeued twice |
| B2 | Full queue returns `Err(QueueError::Full)`; unconsumed slots are never overwritten |
| B3 | `ShardedCuckooTable`: `insert` returning `true` guarantees subsequent `lookup` finds the entry (unless removed or evicted) |
| B4 | CLOCK eviction never leaves `lookup_map` pointing to a dangling read |
| B5 | `Drop` order: `async_worker.join()` completes before `rocksdb.flush()` |

Note on B5: The earlier C++ implementation crashed here (logger destroyed before server pointer in Phase 4a). This prevents destruction-order regressions.

#### Group C: Memory Safety (`miri`)

| ID | Invariant |
|---|---|
| C1 | `rkyv::archived_root` on storage bytes triggers no undefined behavior |
| C2 | `unsafe impl Send/Sync for LockFreeQueue` is sound |
| C3 | Dropping a non-empty queue does not leak `Node<T>` allocations |

#### Group D: Durability Semantics (Integration Tests)

| ID | Invariant |
|---|---|
| D1 | Immediate mode: `PUT` returning `Ok` survives `kill -9` |
| D2 | Batch mode: `PUT` returning `Ok` does not guarantee persistence; test asserts documented write-behind semantics |

D2 matters because write-behind is a deliberate tradeoff. If documentation promises one behavior and code does another, operators lose data and blame Kallisto. Tests must lock down the documented contract, not an imagined stronger one.

#### Group E: Security (Standard Unit/Integration Tests, Blocking)

| ID | Invariant |
|---|---|
| E1 | No plaintext secret values or secret paths appear in `Debug`, `Display`, error messages, or logs (see ADR-0011 §5) |
| E2 | Token comparisons execute in constant time |
| E3 | Explicit `deny` overrides `allow` when both match in policy evaluation |

### 4. Rollout Phases

| Phase | Scope | Dependencies |
|---|---|---|
| **V0** | `cargo-mutants` baseline + `miri` across existing `unsafe` blocks | None. Runs parallel to Phase 3 |
| **V1** | Extract `kallisto_kv_model` + `proptest` model oracle (`BTreeMap` reference implementation) -> Group A | V0 |
| **V2** | `loom` tests for `LockFreeQueue` and `ShardedCuckooTable` -> Group B | None |
| **V3** | `cargo-fuzz` for HTTP parser and rkyv deserialization into the empty `fuzz/` directory | None |
| **V4** | Pilot `Creusot` on `kallisto_kv_model` | V1 |
| **V5** | `TLA+` specifications for lease invalidation and gossip before writing control/data plane code | 1.2.0 |

### 5. Makefile Targets and CI Pipeline

```makefile
make verify   # proptest + miri          - BLOCKING, every PR
make loom     # loom                     - nightly schedule (slow)
make fuzz     # cargo-fuzz, 15m/target   - nightly
make prove    # creusot                  - advisory, allowed to fail
make mutants  # cargo-mutants            - weekly, reports mutation score
```

Only `make verify` sits on the PR critical path. The rest run in the background. If a background job fails three consecutive times without a fix, remove it from CI. A permanently failing job is worse than no job.

## Instructions for AI Agents

This section is read directly by agents.

### Research Tasks (Complete Before Writing Code)

1. **Verify Creusot builds.** Creusot 0.11.x requires `opam`, Why3, and an SMT solver, pinned to a specific Rust nightly. Test the build in a container. If setup exceeds 2 hours or conflicts with workspace toolchains, stop and report immediately. Do not improvise workarounds. Cancelling Tier 2 does not affect Tier 1.
2. **Audit KV-v2 semantics against upstream Vault source.** Check `max_versions` trimming, `delete_version_after`, `cas_required`, and `undelete` behavior on destroyed versions. Cite file paths and line numbers from `hashicorp/vault`. Never guess from memory.
3. **Audit A7 and A9 against the current codebase.** State clearly whether each is a bug or not, why, and provide code evidence.

### Constraints

* Never alter public APIs solely to satisfy verification tools.
* Do not introduce new `unsafe` blocks. Follow `AGENTS.md`.
* Every invariant test must be fail-able: demonstrate that the test fails on deliberately broken code before committing. A test that passes on all inputs tests nothing.
* Never add `#[cfg_attr(miri, ignore)]` to make CI pass. If Miri fails, either fix the code or write an ADR explaining why the pattern is sound and acceptable. There is no middle ground.
* Report all unproven invariants with clear justifications. An unproven invariant list is as valuable as the proven list.

### Definition of Done per Phase

* All invariants in scope have corresponding fail-able tests.
* Makefile target runs cleanly on a clean machine (standard `make` and `rustup` only).
* CI jobs are wired to the blocking or advisory tiers specified in Section 5.
* Uncovered or unproven invariants are documented with explicit justifications.

## Consequences

### Positive

* Catches domain logic bugs deterministically rather than by chance.
* Provides an objective gate for agent-generated code: provers and model checkers do not nod along or get persuaded.
* Gives the CNCF Sandbox application verifiable evidence of engineering rigor.
* Extracting `kallisto_kv_model` improves the architecture even if formal verification is later abandoned.

### Negative

* Increases build complexity and CI duration.
* Creusot's dedicated nightly will clash with the workspace toolchain (10 breaking releases across versions 0.8 through 0.11 in five months).
* Proof maintenance overhead: refactoring `apply` requires updating associated proofs.
* Resource risk: verification effort could drain time from Phase 3 and 4. Mitigated by keeping only `make verify` on the blocking PR path.

### Trusted Computing Base: What Correctness Actually Means Here

Stated plainly to avoid self-deception.

All proofs hold only relative to: `rustc`, LLVM, SMT solvers, Creusot's Rust-to-Coma translation, `redb`, `rkyv`, `openraft`, the Linux kernel, and underlying hardware. None of these are verified by Kallisto.

Most critically: proofs confirm code matches the specification, not that the specification matches user intent. If we misunderstand Vault's `max_versions` semantics, Creusot will happily prove our misunderstanding completely correct. This is why `tests/e2e_vault_compat.rs` remains irreplaceable: it anchors our specification to external reality.

### Out of Scope

* Whole-codebase formal verification.
* Common Criteria / EAL certification.
* Verifying third-party dependencies (`redb`, `rkyv`, `openraft`, RocksDB).
* Microarchitectural side-channel defenses (Spectre, cache timing). E2 covers application-level constant-time comparisons only.
