## Context and Problem Statement

Kallisto needs to determine its user interface strategy for both local node diagnostics and fleet-wide observability. The decision involves choosing between building a WebUI (either node-local or centralized as Kalena) and a Terminal User Interface (TUI), considering the security implications of Kallisto running as a DaemonSet across hundreds of nodes.

## Decision Drivers

* Kallisto is deployed as a DaemonSet across a large fleet (e.g., 500+ nodes). Adding a WebUI to every node significantly increases the network attack surface (requiring TLS, auth, and CVE patching).
* A WebUI displaying secrets on every node multiplies the risk of secret exposure.
* Node-local diagnostic tools should inherit existing trust boundaries (e.g., SSH) rather than creating new network ports.
* A centralized WebUI (Kalena) would need to handle a complex version matrix across multiple projects (Kallisto, Helvilette, Kuberina) and would become a high-value target (a god-mode credential store).
* Kallisto's API is still evolving, making a centralized UI premature.
* Observability tools like Prometheus and Grafana are already standard in the target infrastructure.

## Considered Options

* WebUI on Data Plane (per node)
* Centralized WebUI (Kalena)
* Embedded TUI for node-local operations + Grafana for fleet-wide metrics

## Decision Outcome

Chosen option: Embedded TUI + Grafana, because TUI leverages the existing SSH trust boundary without adding any network attack surface, making it ideal for secure node-local diagnostics. Fleet-wide observability is delegated to Prometheus and Grafana, avoiding the complexity and security risks of building a centralized WebUI.

WebUI on the data plane is strictly forbidden. The development of Kalena (the centralized WebUI) is postponed until the APIs of all related projects are stable.

### Consequences

* Good, because it prevents adding 500+ administrative HTTP endpoints to the fleet, keeping the attack surface minimal.
* Good, because TUI provides immediate, localized diagnostics even on edge nodes with poor connectivity or no browser access.
* Good, because it avoids the maintenance nightmare of a centralized UI dealing with a shifting version matrix.
* Good, because it leverages the platform team's existing Grafana infrastructure for free.
* Bad, because it lacks a unified, click-driven graphical interface for operators who prefer WebUIs over terminals.

### Confirmation

* The TUI will communicate with the Kallisto daemon via a Unix socket with strict file permissions, not a network port.
* The TUI will be strictly read-only.
* The TUI must **never** display secret values (even in Sovereign mode). Secret access must go through the API for audit logging.
* Kallisto will expose Prometheus metrics, and a dashboard.json will be provided in the repository.

## Pros and Cons of the Options

### WebUI on Data Plane

* Good, because it provides a familiar interface for operators.
* Bad, because it exposes administrative endpoints on every node, drastically increasing the attack surface.
* Bad, because managing auth, TLS, and vulnerabilities for hundreds of UI endpoints is a massive operational burden.

### Centralized WebUI (Kalena)

* Good, because it offers a single pane of glass for the entire stack.
* Bad, because it becomes a single point of compromise holding credentials for the entire fleet.
* Bad, because maintaining compatibility across multiple evolving projects (Kallisto, Helvilette, Kuberina) is currently unsustainable.

### Embedded TUI + Grafana

* Good, because the TUI operates within the existing SSH session's permissions.
* Good, because it explicitly separates node-local troubleshooting (TUI) from fleet-wide trends (Grafana).
* Neutral, because while it doesn't provide a centralized control UI, it perfectly fulfills the operational need for diagnosing specific pod failures.

## More Information

### TUI Design & Requirements

The TUI is designed for diagnostic purposes (answering why a request failed), not just monitoring.

Proxy Mode Screens:
1. Health (Default): Displays upstream status, token TTL countdown (critical to prevent silent failures), and cache hit rate.
2. Request Diagnostics: Shows recent requests with SO_PEERCRED (identifying the exact requesting process), hit/miss status, age, and failure reasons.
3. Freshness: Shows TTL configuration, median/oldest secret age, and event stream connection status.
4. Exposure: Shows the exact amount of plaintext in memory vs the configured ceiling.

Sovereign Mode Screens:
1. Durability (Default): Shows storage usage, Raft log unpurged entries, and crucially, the last snapshot time and its verification status (kallisto verify-snapshot).
2. Structure: Displays mount points and policies (no secret values).
3. Recent Writes: Audit log of who wrote to which path and when.
4. Cluster: Raft cluster status (leader, peer lag).
5. Risk Debt: A unique screen showing secrets that have never been read or updated for extended periods, highlighting unused secrets that pose pure risk.

Security Considerations:
The TUI reads via a Unix socket. To protect the organization's secret catalog in multi-tenant environments, a --redact-paths flag will be available to only show mount prefixes instead of full paths. TUI access itself will generate an audit log entry.
