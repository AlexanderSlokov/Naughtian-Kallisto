# ADR-0005: Split Kallisto into Dataplane and Controlplane

## Context and Problem Statement

Kallisto began as a single component: a node-local cache sitting in front of a Root of Trust (Vault, OpenBao, Infisical). That design has two ceilings that cannot be raised from inside a single-component architecture.

The first is the **freshness/load tradeoff**. A pure cache has exactly one knob — TTL. A long TTL keeps upstream load low but makes revocation slow; a short TTL makes revocation fast but pushes load back onto the upstream that Kallisto exists to protect. There is no setting that satisfies both, because there is nobody to tell a node that a secret has changed.

The second is **credential blast radius**. Without coordination, every node must hold its own upstream credential, scoped broadly enough to cover any workload that might be scheduled onto it. A 500-node fleet is 500 broadly-scoped credentials.

Separately, an earlier draft of this project imagined a standalone persistent mode ("Sovereign") as a self-contained secret store. That framing was rejected: defined as *a kind of thing* (a secret store), it has no principle by which to refuse features, and drifts toward becoming a worse Vault.

This ADR records the decision to split Kallisto into two roles, and to define the second one by **what it is for** rather than **what it is**.

## Decision Drivers

* Revocation latency must be decoupled from cache TTL.
* Upstream credentials held on nodes must be short-lived and narrowly scoped.
* Cold start after a rolling restart, and stampede after upstream recovery, both require fleet-level coordination that no single node can perform.
* There is currently no incident-response primitive anywhere in the secrets ecosystem for "purge this leaked secret from every node, now."
* Kallisto must not become a lesser Vault. It needs a boundary that refuses features structurally, not by willpower.
* The dataplane must remain fully useful when no controlplane exists. Adding a controlplane must not introduce a single point of failure into the data path.
* Deployment reality is Kubernetes DaemonSets and edge sites with no on-site operator.

## Considered Options

* **A — Single component, cache only.** Status quo. TTL is the only control.
* **B — Single component that can also be a standalone secret store.** A Vault alternative, self-contained, HA via Raft.
* **C — Two roles: Dataplane and Controlplane.** The controlplane coordinates a fleet of dataplanes; it may or may not also own secrets.

## Decision Outcome

Chosen option: **C — Dataplane and Controlplane**.

**Kallisto Dataplane** runs on every node. It answers secret reads locally, holds the cache, and enforces caller authorization. It talks to an upstream Root of Trust directly by default.

**Kallisto Controlplane** coordinates the fleet: it pushes invalidations, brokers scoped short-lived credentials, pre-warms caches ahead of a rollout, paces stampedes, and aggregates fleet-wide exposure telemetry. It may run in front of an upstream Root of Trust (holding no organizational secrets at all), or as the source of truth where no upstream exists.

The controlplane is defined by its **role**, not its nature. Every proposed feature must answer one question: *does this help coordinate the fleet?* If not, it is out of scope. This is the mechanism that keeps Kallisto from drifting into Vault's problem space.

Option B is rejected because a component defined as "a secret store" has no principled way to say no, and because it puts Kallisto into direct competition with Vault and OpenBao on their own axis, where its differentiators do not apply.

### Consequences

* Good, because the freshness/load tradeoff is escaped rather than tuned: a long TTL keeps upstream load low, while pushed invalidation gives revocation effect in milliseconds. This is a change of kind, not a change of degree.
* Good, because credential brokering collapses N broad node credentials into one controlplane identity plus N narrow, short-lived, per-node tokens. Compromising a node yields only that node's scope, for only a few minutes.
* Good, because fleet-level incident primitives become possible — purge a leaked secret everywhere, drain a suspect node — which exist in no comparable product today.
* Good, because cold-start warming and upstream-recovery pacing are solvable at all. In a single-component design they are not.
* Good, because the controlplane can sit in front of Vault or OpenBao without owning any organizational secret, so adopting Kallisto does not require replacing an existing Root of Trust.
* Good, because controlplane outage degrades management, not the data path. The dataplane keeps serving from cache and keeps reaching upstream directly.
* Bad, because there is now a second component to build, deploy, secure, document, and test.
* Bad, because the command channel becomes a higher-value target than the data channel: anything the controlplane can do for the fleet, an attacker who controls it can do to the fleet.
* Bad, because two deployment topologies (with and without controlplane) must both be supported and tested indefinitely.
* Bad, because in brokered mode a cache miss gains one additional hop.

### Confirmation

* The dataplane test suite must pass with no controlplane configured. This is the fitness function for "controlplane is optional."
* An integration test must kill the controlplane mid-run and assert that the dataplane continues serving cached reads *and* continues reaching upstream for misses.
* The `role:` tagged enum in configuration (see ADR-0003) makes dataplane and controlplane settings mutually exclusive at parse time.
* The command channel requires mTLS, and every command must carry a verifiable origin. A command with unverifiable origin is refused, not logged-and-executed.
* Metrics must expose `kallisto_passthrough_active` so that degraded operation is visible rather than silent.

## Pros and Cons of the Options

### A — Single component, cache only

* Good, because it is the smallest thing that works, and it is genuinely optional: remove it and the workload talks to upstream directly.
* Good, because it has no coordination surface to attack.
* Neutral, because it remains the correct shape for small deployments and is what the dataplane still is.
* Bad, because revocation latency is bounded below by TTL, and lowering TTL returns load to the upstream.
* Bad, because every node needs its own broadly-scoped upstream credential.
* Bad, because there is no way to warm a cold fleet, pace a stampede, or purge a leaked secret.

### B — Single component that can also be a standalone secret store

* Good, because it needs no second component and no new deployment topology.
* Good, because it addresses the edge case where no upstream Root of Trust exists.
* Bad, because "a secret store" as a definition admits every feature Vault has, with no principle for refusing any of them.
* Bad, because it competes with Vault and OpenBao directly, where "lighter" is an eroding advantage that disappears one feature request at a time.
* Bad, because being the source of truth makes HA non-negotiable, which drags in consensus, which is the most expensive thing on the roadmap.

### C — Dataplane and Controlplane

* Good, because the controlplane is defined by role, and a role-based definition can refuse features on its own.
* Good, because it solves the two ceilings (freshness/load, credential blast radius) that motivated the split, and neither is solvable in A or B.
* Good, because the availability question dissolves: the dataplane fleet *is* the availability tier for the controlplane.
* Neutral, because it borrows its shape from Kong's hybrid CP/DP model — a structural analogy, not a domain one. Individual decisions still need independent justification.
* Bad, because it doubles the deployment surface and adds a high-value command channel.

## More Information

### The boundary that keeps the controlplane from becoming Vault

Two rules, both structural rather than discretionary:

**1. Never generate credentials.** Kallisto never creates anything in a system it does not own. Issuing a token for access to itself is fine — it is self-referential and dies with the process. Creating a database user is not. The moment you `CREATE USER` in someone else's database, you must remember you did; crash between creating it and recording the lease and there is a live account nobody knows about, forever. Avoiding that orphaned state is what requires lease stores, revocation queues, write-ahead logs, and startup reconciliation — roughly 80% of Vault's mass. This boundary is binary, not a matter of degree, so "lighter than Vault" here is a structural consequence rather than an eroding advantage.

**2. Fleet-owned versus organization-owned secrets.** The controlplane may hold secrets that exist *because the fleet exists* — certificates for the load balancer fleet, inter-node keys. It must not hold secrets that exist independently of Kallisto — database passwords, third-party API keys. Those belong to the upstream, and Kallisto only caches them.

### Availability

The dataplane fleet is the availability tier. Controlplane downtime means loss of coordination, not loss of secrets: dataplanes continue serving from cache and continue reaching upstream directly.

Therefore a single-node controlplane with verified periodic snapshots is acceptable for the first release. Raft is deferred until there is a user requirement that a single lost write is unacceptable *and* automatic leader election is required. When that time comes, use `openraft` or `raft-rs`; do not hand-roll consensus.

### Relationship to gossip

The controlplane and the Foca/SWIM gossip layer are complementary, not alternatives:

> The controlplane **originates and authorizes** commands. Gossip **propagates** them.

The controlplane speaks to a handful of nodes; gossip fans out to the rest. This gives an accountable origin for every command (which gossip alone lacks) and fan-out that does not depend on a single reachable point (which the controlplane alone lacks). Invalidation messages carry no secret material, so gossiping them is safe.

### Upstream reachability mode

Two modes, trading against different threats. `direct` is the default because it preserves the "dataplane works without controlplane" invariant.

```yaml
upstream:
  mode: direct     # DP talks to upstream. Survives CP outage.
                   # Preserves per-workload attribution in upstream audit logs.
  mode: brokered   # DP talks only to CP. Upstream is network-isolated.
                   # Requires CP HA. Upstream audit collapses to one identity.
```

`brokered` is worth naming explicitly because its cost is not obvious: once the controlplane fetches on behalf of every node, the upstream's audit log records only the controlplane as the reader, permanently. Kallisto then becomes the sole source of truth for "who read what," which is a compliance obligation, not just a feature.

### Naming

Codenames stay in documentation; configuration values stay boring and guessable:

```yaml
role: proxy          # dataplane
role: control-plane  # controlplane
```

### Supersedes

This ADR supersedes the "Sovereign Mode" framing used in earlier design notes. Sovereign was defined as a standalone secret store; the controlplane is defined as a fleet coordinator that may optionally also be authoritative.
